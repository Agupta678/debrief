01 Problem

Meetings produce decisions and commitments, but they live in scattered raw notes — bullet points, shorthand, half-sentences typed during the call.

Nobody goes back and turns that mess into something a stakeholder who wasn't in the room can actually read. Commitments made in the room quietly die after the room empties, and the person who owns the recap ends up rewriting their own notes from scratch anyway.

02 Product

Debrief takes raw, messy meeting notes and turns them into one clean, shareable document — the kind you'd actually paste into a Slack message or email to stakeholders. Not a list of extracted chips: a document with a title, a plain-language summary, the decisions that were made, the action items with owners, and the open questions still hanging.

Positioning

"Paste your notes. Get the update you were going to have to write anyway."

2.1 Why this scope, not the broader one

General "AI meeting notes" tools already do transcription and summarization broadly, and compete on breadth of integrations. Debrief stays narrow: it doesn't record, doesn't integrate with a calendar, doesn't manage a workspace. It does one thing — turn raw notes into the specific document shape a stakeholder update needs — and does it well.

A user-selectable template gallery was the original idea, and was deliberately deferred. Shipping a template picker before proving one template earns trust dilutes the niche into "yet another AI notes tool." One strong opinionated default, refined until it's reliably good, is the actual differentiator.

03 Goals & non-goals

This phase ships one default template, end to end, deployable, and honest about how well it works.

  1. Ship one default document template — the Stakeholder Update — generated via a Claude-powered extraction endpoint.
  2. Make the output shareable: copy as Markdown, download as a .md file, no account or storage required.
  3. Keep a deterministic local fallback so the tool degrades gracefully instead of going blank if the API call fails.
  4. Track extraction quality with a checked-in benchmark rather than an unverified claim on the landing page.
  5. Ship as a deployable app — serverless function, env-based config — not a folder of static files run locally.

In scope

  • Single Stakeholder Update template
  • Copy / download as Markdown
  • Heuristic fallback engine
  • Checked-in benchmark script

Not this phase

  • Template picker / multiple formats
  • Accounts, saved history, workspaces
  • Calendar, Slack, or Jira integrations
  • In-UI editing of extracted items
  • Mobile app / browser extension

04 Users

Anyone who leaves a meeting with a wall of raw notes and needs to produce a clean stakeholder-facing update without manually rewriting it. A single-purpose utility, not a workspace — no persona segmentation needed for this phase.

05 Document schema

The "Stakeholder Update" shape both the Claude endpoint and the local heuristic fallback must produce, so the rendering layer never needs to know which engine ran.

{
  "title": "string — short, specific (e.g. \"Q3 Roadmap Sync — Aug 18\")",
  "summary": "string — 2–4 plain-language sentences, read first",
  "decisions": ["string — a decision actually made, not discussed"],
  "actionItems": [
    {
      "task": "string",
      "owner": "string (\"Unassigned\" if unclear)",
      "due": "string | null — free text, e.g. \"Friday\" (not date-normalized)",
      "status": "blocking | pending | open"
    }
  ],
  "openQuestions": ["string — unresolved items, risks, blockers"]
}

Status is inferred, not asserted: blocking for urgent/escalation language, pending for anything with a due signal, open for anything without one.

06 Requirements

6.1 Extraction API

EndpointPOST /api/extract — Vercel Node serverless function
Input{ notes: string }, capped at 20,000 characters
Implementation@anthropic-ai/sdk, client.messages.parse() with a Zod schema (output_config.format) for guaranteed-shape output
Modelclaude-opus-5, overridable via CLAUDE_MODEL
Key handlingANTHROPIC_API_KEY read server-side only — the reason extraction is a backend call, not client-side
Failure behaviorAuth, rate-limit, timeout, or missing-key errors return a typed non-2xx; the client falls back to the local heuristic rather than showing a blank state

6.2 Local heuristic fallback

Extended from an action-item-only engine to approximate the full document shape: title from the first short non-action line (else a default), a generated one-line summary, decisions matched via decision-language patterns, action items via existing owner/due logic, and open questions from "open" signal patterns plus lines ending in ?.

Always available, always instant, always client-side — this is what powers the landing page's live demo panel too.

6.3 Quality benchmark

benchmark/fixtures.json holds hand-written raw-notes examples with expected documents, covering clear ownership, implied ownership, no owner, explicit vs. relative due dates, no date, blocking language, and lines that should not be extracted.

benchmark/score.mjs runs the fixtures through both engines and reports accuracy — always against the local heuristic, and against the live Claude endpoint when ANTHROPIC_API_KEY is set. Output is a reproducible report, not a landing-page claim.

6.4 Front-end

  • The "Try it" tool renders a document, not a chip grid — title, engine badge, summary, decisions, action items, open questions.
  • Loading state while /api/extract is in flight.
  • "Copy as Markdown" and "Download .md" in the output panel — the actual share mechanism for this phase.
  • Silent fallback to the heuristic on API failure, with a small indicator of which engine produced the result.
  • The hero demo panel stays on the static local heuristic — no reason to spend a live API call rendering the same canned example on every page load.

6.5 Deployment

  • package.json with @anthropic-ai/sdk and zod as dependencies — no build step for the static front-end.
  • No vercel.json needed — static root files plus api/ is Vercel's zero-config convention.
  • .env.example documents ANTHROPIC_API_KEY and CLAUDE_MODEL; .env is gitignored.

07 Deferred to v2

Out of scope now, but the schema and architecture are deliberately built so none of this requires a rearchitecture later.

  • Template picker — additional document shapes ("Status Report," "Decision Log," "Exec Summary") plus auto-detection of the best template from note content. The schema in §5 is generic enough that a second template is an additive schema and prompt, not a rewrite.
  • Date normalization — resolving "next Monday" to an ISO date against a reference date.
  • Hosted, shareable link output instead of copy / download only.
  • Rate limiting and abuse protection on the public endpoint — no auth currently planned; acceptable for a personal-project launch, revisit before meaningful traffic.

08 Success criteria

  • The Claude endpoint produces a document that a real stakeholder update could plausibly be pasted from, on real messy notes — not just the curated hero example.
  • The benchmark script runs clean from a fresh clone and produces a report, backing the "tracked in the repo" claim on the landing page.
  • The app is deployable to Vercel with only an API key as required configuration.
